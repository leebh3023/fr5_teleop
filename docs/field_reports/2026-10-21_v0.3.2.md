## 3. 상세

### 3-1 갱신
- 기존 상태는 v0.3.0 detached HEAD였고 로컬 수정(`config.yaml`, `control_math.py`, `test_control_math.py`)이 있었다.
- `control_math.py`와 테스트 수정은 v0.3.1에 이미 같은 내용이 들어 있어 버렸다. 이전 상태는 `git stash@{0}`에 남아 있다.
- `.env`의 `TELEOP_TAG`는 0.3.0이었고 0.3.2로 바꿨다 (`.env`는 커밋하지 않는다).
- 인증서: 기존 SAN은 `192.168.1.50`뿐이라 Quest 접속 주소 `192.168.0.63`으로 다시 만들었다 (SAN `192.168.0.63`, `127.0.0.1`). 기존 인증서는 저장소 밖 `~/cert_backup/`에 백업했다.

### 3-6 카메라
- **USB 연결 문제와 해결**: 처음에 `lsusb -t`에 `480M`(USB 2.1)으로 보였고, 다시 꽂은 뒤에는 장치가 아예 보이지 않았다. 커널 로그에 `usb usb4-port2: Cannot enable. Maybe the USB cable is bad?`가 4초 간격으로 반복됐다. 짧은 케이블로 바꾸자 Bus 2에서 `5000M`(USB 3.2)으로 정상 인식됐다. 원인은 케이블이었다.
- **재연결 시험**(dry-run 중 뽑았다 꽂음):
  - 05:36:23 `camera read failed: Device disconnected. Failed to reconnect: No device connected1000; restarting stream`
  - 이후 2초 간격 `camera start failed: no RealSense device connected; retrying in 2 s`
  - 05:36:45 `camera streaming name=wrist ...` 로 복귀. `/health`의 camera는 `streaming: True`, 약 29.98fps, `last_error: None`
  - 작업자: `/monitor`가 초록으로 돌아왔고 30fps. 컨테이너 재시작 없음
  - 복귀 후 녹화 `episode_000003`: 10.64초, 영상 319프레임, `dropped_frames=0`, `error=null`
- **meta.json cameras.wrist(episode_000004)**: `frames=804`, `dropped_frames=0`, `error=null`, h264 (libx264 crf 18, yuv420p), timestamp domain `global_time`.

### 하드웨어 모드 녹화(episode_000004)의 `missed_ticks`
- 시작 전 0, 종료 후 778.
- 05:40:11 시점까지는 약 2,360 서보 틱 동안 20 (약 0.8%). 카메라 없는 첫 세션(73/7,596, 약 1%)과 같은 수준이라 카메라 인코딩의 영향은 보이지 않았다.
- 나머지 약 750은 05:40:13~18에 트리거를 연속으로 눌렀을 때 생겼다. `move_gripper`가 1.57초, 1.50초, 1.81초씩 걸렸고(각각 197, 188, 227틱 누락), 직후 `servo_start`도 1.13초 걸렸다(142틱 누락). 모두 `GRIPPER_ACTION`, `SLEEPING`, `ARMING` 상태였고 서보 추종 중(`ACTIVE`)은 아니었다.
- 같은 시각 Quest 로그: `client telemetry degraded ... suspected=controller_tracking`, `pose stream gap receive_gap_ms=2143.3`. 컨트롤러 추적이 약 2초 끊긴 구간이다.

## 4. 실패/보류 항목과 관찰 사항

1. **보류: 로그의 SDK/펌웨어 버전이 문서와 다르다.**
   - 증상: `Fairino connection ready: ip=192.168.57.3 versions=['SDK:V2.2.7', 'Robot:V3.9.7']`. `docs/ROBOT_VERSION_COMPATIBILITY_KO.md` 57행은 "SDK 2.2.8이 나오는지 확인"이라고 하고, 지시서는 펌웨어 v3.9.8을 기대한다.
   - 이 로봇의 실제 펌웨어가 3.9.7인지, 2.2.8 SDK가 내부적으로 V2.2.7이라고 보고하는지는 현장에서 구분하지 못했다. 연결과 동작은 정상이었다.
   - 컨트롤러 웹 화면에서 펌웨어 버전을 확인해야 한다.
2. **관찰: `move_gripper` 호출이 간헐적으로 1.5~1.8초 걸린다.** 첫 녹화 세션(카메라 없음)에서도 1.56초 한 번(`missed_ticks` 약 196 증가), 카메라 세션에서는 세 번 있었다. 평소 호출은 약 15ms다. 서보 중에는 일어나지 않았지만 `missed_ticks`를 크게 올린다. 연속 트리거 입력 때 더 잘 생겼다.
3. **관찰: Quest 컨트롤러 추적 끊김.** `telemetry degraded ... suspected=controller_tracking` 경고가 녹화 세션과 첫 하드웨어 세션에서 나왔다. 컨트롤러를 시야 밖에 두면 생기는 것으로 보이며, 작업자에게 이 시점의 상황은 확인하지 못했다.
4. **관찰: 처음 하드웨어 시작 때 `slow SDK call summary ... operation=connect last_ms=317`.** 매번 시작 때 한 번 나온다.
5. **카메라가 D435(IMU 없음)다.** 640x480 컬러 30fps, depth 끔 설정에서는 영향이 없었다. 컨테이너 장치 이름이 `D435`로 나와 지시서의 기대 문자열 `D435I`와 다르다.
6. **지시서와 다른 환경**: 로봇이 두 대(FR3 `.57.2`, FR5 `.57.3`)라 IP가 지시서와 다르다. 호스트에 librealsense udev 규칙이 이미 있어 지시서의 `install_realsense_udev.sh`를 실행하지 않았다.

## 5. 현장에서 바꾼 `config.yaml` 값

`git diff config.yaml` (v0.3.2 `main` 기준):

| 키 | 값 | 이유 |
|---|---|---|
| `robot.ip` | `192.168.57.2` → `192.168.57.3` | 이 로봇은 FR5(.57.3), .57.2는 FR3. 작업자가 직접 설정 |
| `motion.workspace.x` | `[-600, 600]` → `[-100, 800]` | 현장에서 실제로 검증한 작업 범위. 작업자가 처음 `[-100, 700]`으로 바꾸고 녹화 세션 직전에 800으로 늘렸다 |
| `recording.camera.enabled` | `false` → `true` | 3-6 카메라 검증을 위해 작업자 동의 후 변경 |

`gripper.enabled`는 최신 `main`(99ff85d)에 이미 `true`로 들어 있어 별도 변경이 아니다. 지시서(v0.3.2 태그 시점)는 `false`를 가정하고 그리퍼 검증을 요구하지 않는데, 이 현장은 그리퍼를 연결해 쓰고 있다. 녹화 세션 중 트리거 6회가 모두 완료됐다(`gripper_command_count=6`, `gripper_complete_count=6`, `fault` 없음). 작업자 답변: 그리퍼 사용에 이상 없음 (육안 확인은 "녹화 완료" 답변 외에 따로 받지 않았다).

## 6. 개발 PC 후속 작업 제안

1. **그리퍼 호출 지연**: `move_gripper`가 1.5초 이상 걸릴 때 서보 루프가 막히는 것을 완화할 방법(별도 스레드, 타임아웃, 연속 트리거 억제)을 검토. 서보가 꺼진 상태에서만 일어나지만 `missed_ticks` 지표를 오염시킨다.
2. **SDK/펌웨어 버전 표기**: `versions=['SDK:V2.2.7', 'Robot:V3.9.7']`가 번들 SDK 2.2.8과 일치하지 않는 이유 확인. 문서의 "SDK 2.2.8이 나오는지 확인" 절차를 실제 출력에 맞게 수정하거나, 로그에 번들 SDK 버전을 따로 찍는 것을 검토.
3. **문서 보강**:
   - 호스트에 librealsense udev 규칙이 이미 있을 때 `install_realsense_udev.sh`가 필요한지 안내.
   - 카메라 USB 3 연결 실패 시 케이블 교체 안내(커널 로그의 `Cannot enable. Maybe the USB cable is bad?`).
   - D435(IMU 없음)도 지원 대상임을 명시하고, 지시서의 기대 문자열(`D435I`, `0b3a`)을 모델 무관하게 고침.
   - 로봇이 여러 대인 현장의 IP 설정 안내.
4. **`make_cert.sh`**: 기존 인증서가 접속 주소를 포함하지 않으면 경고만 하고 만들지 않는다. 지우고 다시 만드는 절차를 안내하거나, 백업 후 재생성 옵션을 제공하는 것을 검토.
5. **`.gitignore`**: 인증서를 `certs/` 아래 하위 폴더로 백업하면 무시되지 않는다(`certs/*.pem`만 무시). `certs/**`로 넓히는 것을 검토.
